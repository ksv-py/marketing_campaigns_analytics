CAMPAIGN LENS - PROJECT AND INTERVIEW GUIDE
============================================

PROJECT SUMMARY
---------------
Campaign Lens is a customer marketing response analysis project. It turns the original Marketing Campaign customer export into a small decision-focused dashboard. The dashboard helps a marketing or CRM team compare campaign response, customer segments, preferred channels, observed product spend, and response propensity signals.

The project is inspired by the business direction of the reference repository, but the application code, narrative, derived fields, and dashboard are original. The project uses the original public Marketing Campaign dataset rather than synthetic data.

WHAT THE DASHBOARD SHOWS
------------------------
1. Customers in the currently selected audience.
2. Overall response rate for that audience.
3. Observed product spend associated with the audience.
4. Average observed spend per customer.
5. Response rate by campaign grouping.
6. Response rate and audience size by customer segment.
7. Channel-level customer count, response rate, and observed revenue.
8. A baseline logistic regression response propensity model.
9. Directional model signals that support or reduce predicted response.

The sidebar lets the user filter by education, preferred channel, and income range. Charts and summary metrics recalculate from the filtered data.

DATA SOURCE AND PREPARATION
---------------------------
Source dataset:
https://www.kaggle.com/datasets/rodsaldanha/arketing-campaign

The source file is stored locally as:
data/marketing_campaign.csv

The original export contains customer demographics, income, household information, signup date, recency, product spending, purchase channels, campaign acceptance flags, complaints, and the final Response field.

The loader in analysis.py:
- Reads the original semicolon-delimited CSV.
- Removes rows without income because income is used for segmentation and filtering.
- Renames source fields into readable dashboard fields.
- Derives preferred channel from web, catalog, and store purchase counts.
- Derives income-based customer segments.
- Groups campaign acceptance flags into an earlier-campaign indicator.
- Sums product spending into revenue_influenced.
- Sums web, catalog, and store purchases into prior_purchases.

MODEL EXPLANATION
-----------------
The model is a logistic regression baseline. Categorical fields are one-hot encoded and numeric fields are standardized in a scikit-learn ColumnTransformer pipeline. The data is split into training and test sets with stratification on the Response field. The model is evaluated with ROC AUC because the task is binary response ranking.

The model is not presented as a causal model. A positive coefficient means the feature is directionally associated with a higher predicted response in this sample. It does not prove that changing the feature will cause a customer to respond.

CURRENT RESULT
--------------
With the original dataset and the current fixed split:
- 2,216 records are loaded after removing missing income values.
- The overall response rate is approximately 15.03%.
- The baseline model achieved approximately 0.722 ROC AUC.

These figures describe this dataset and this evaluation setup. They should not be presented as production performance.

LIKELY RECRUITER QUESTIONS AND STRONG ANSWERS
----------------------------------------------

Q1. Walk me through the project.
A: I built a marketing response analysis tool using the original Marketing Campaign customer dataset. I loaded and cleaned the export, engineered practical business fields such as preferred channel, income segment, total product spend, and prior purchases, then built a Streamlit dashboard. The dashboard compares campaign and channel response and includes a logistic regression baseline for response ranking. My emphasis was on turning analysis into decisions while being transparent about what the data can and cannot prove.

Q2. What business problem does this solve?
A: It helps a CRM or marketing team identify which audiences and channels have historically produced stronger responses. It supports campaign prioritisation and audience review. It does not claim to measure incremental campaign lift because there is no randomized control group in the source data.

Q3. Why did you use this dataset?
A: It contains customer demographics, household context, recency, product spending, purchasing channels, campaign acceptance history, and a response outcome. That gives enough structure to demonstrate data preparation, descriptive analysis, segmentation, and a supervised learning baseline in one coherent project.

Q4. What was the most important data-cleaning decision?
A: I handled the semicolon-delimited source format explicitly and removed records without income because income is required for the dashboard's income filter and segment derivation. I would separately profile missingness and outliers before using this workflow in production.

Q5. Why is the source file semicolon-delimited?
A: The original export uses semicolons as separators. Assuming commas would produce one giant column, so the loader specifies sep=';' and validates required source columns before continuing.

Q6. How did you define customer segments?
A: I used simple income bands: below 35,000 as Value conscious, 35,000 to 65,000 as Growing, and above 65,000 as Established. These are analytical labels for exploration, not official customer personas. In a real project I would validate them with stakeholders and test whether they improve decision quality.

Q7. How did you define preferred channel?
A: I compared each customer's web, catalog, and store purchase counts and assigned the channel with the strongest observed activity. This is a behavioral proxy, not a channel preference directly stated by the customer. Ties fall back to store in the current implementation, which is a limitation worth documenting.

Q8. What does revenue_influenced mean?
A: It is the sum of observed product spend fields in the source data. The name is used for dashboard context, but it should not be interpreted as causal campaign revenue or campaign lift. A controlled experiment would be needed to estimate incremental revenue.

Q9. Why did you choose logistic regression?
A: It is a strong, interpretable baseline for binary response prediction. It is fast, easy to explain, and produces probabilities that can rank customers for outreach. I would compare it with tree-based models after establishing a leakage-safe validation design.

Q10. Why did you use ROC AUC?
A: The operational use case is ranking customers by response likelihood, so ROC AUC measures how well the model separates responders from non-responders across thresholds. I would also report precision-recall AUC, calibration, lift at the top-k audience, and expected campaign economics because the response class is imbalanced.

Q11. What is class imbalance here?
A: The response rate is about 15%, so non-responders are much more common. Accuracy could therefore be misleading. I would focus on precision, recall, PR AUC, lift, calibration, and business value at the campaign capacity the team actually has.

Q12. What is data leakage and how would you check for it?
A: Leakage occurs when a feature contains information that would not be available at prediction time. I would remove post-campaign fields, define a clear prediction timestamp, use a time-based split, and confirm that campaign outcome fields are not used to predict the same outcome.

Q13. Is the model causal?
A: No. It estimates association and response propensity from historical observations. It cannot tell us whether sending a campaign caused a response. To estimate causal lift, I would use randomized treatment and control groups or a defensible quasi-experimental design.

Q14. How would you improve the evaluation?
A: I would use a chronological train-validation-test split, cross-validation within the training period, probability calibration, PR AUC, top-decile lift, and a cost-benefit threshold. I would also test performance across segments and channels for stability and fairness.

Q15. How would you improve the model?
A: I would add careful feature engineering, compare regularized logistic regression with gradient boosting or random forest, tune the decision threshold to campaign capacity, and monitor drift. I would avoid adding complexity until it creates measurable improvement over the interpretable baseline.

Q16. What are the limitations of the dashboard?
A: The data is historical and observational, campaign identity is simplified into an earlier-campaign/current-offer grouping, preferred channel is inferred, and there is no treatment-control design. The dashboard is a portfolio analysis tool, not a production decision system.

Q17. How would you productionise this project?
A: I would create a scheduled ingestion job with schema checks, version the transformed data, train models through a reproducible pipeline, store metrics and artifacts, expose predictions through a controlled service or warehouse table, and monitor data quality, drift, calibration, and business lift.

Q18. What tests would you add?
A: I would test delimiter and required-column validation, derived segment boundaries, response-rate calculations, empty-filter behavior, model reproducibility, and schema compatibility. I would also add an integration test that loads a small fixture and verifies the dashboard-ready columns.

Q19. How would you protect customer privacy?
A: I would minimize personally identifiable information, avoid exposing customer IDs in public dashboards, restrict access, document retention, and verify consent and legal basis. The public portfolio version should use an approved public dataset or de-identified data only.

Q20. What insight would you present to a stakeholder?
A: I would present differences in response rate and audience size by campaign and channel, then quantify the trade-off between reach and response. I would avoid saying a channel is better without controlling for audience mix, and I would recommend an experiment to validate the most promising allocation.

Q21. Why Streamlit instead of only a notebook?
A: A notebook is good for exploration and reproducibility, while Streamlit makes the analysis interactive for a non-technical stakeholder. The dashboard lets someone filter the audience and immediately see how the business metrics change.

Q22. What happens if the dataset is missing?
A: The app stops with a clear message and links to the documented source. It does not silently generate replacement data, because fabricated data would make the displayed insights misleading.

Q23. How did you make the project humanized?
A: I wrote the dashboard around the questions a marketing team would ask, used plain-language labels, surfaced interpretation caveats, and avoided presenting a model score as an unquestionable answer. The goal is to help someone decide what to investigate next.

Q24. What would you do differently with more time?
A: I would preserve campaign-level definitions, add time-aware modeling, create a proper experiment-readout page, calibrate probabilities, add top-k lift and profit curves, and validate findings with a marketing stakeholder before turning them into recommendations.

SHORT 60-SECOND INTRODUCTION
-----------------------------
I built Campaign Lens, a Python and Streamlit project for analyzing marketing campaign response. It uses the original public Marketing Campaign dataset, cleans the semicolon-delimited export, derives behavioral fields such as preferred channel and income segment, and presents campaign, segment, and channel performance interactively. I also built an interpretable logistic regression baseline that ranks likely responders and achieved about 0.722 ROC AUC on a fixed held-out split. The important part is that I distinguish association from causation: the source data can show historical response patterns, but campaign lift would require a controlled experiment.
